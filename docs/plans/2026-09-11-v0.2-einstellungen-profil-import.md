# Plan v0.2 — Einstellungen als Entities, Lastprofil, Import, Blueprints, Dashboards

Stand 11.09.2026. Ziel: Die Integration ersetzt das private YAML-Paket vollständig (inkl.
„kW-Grenze im Dashboard einstellen“) und liefert Darstellungen, die zeigen, *wann* Spitzen
entstehen.

## Prinzipien

1. **Eine Wahrheitsquelle:** Schwellwerte und Preise leben in `config_entry.options`. Number-Entities
   und Options-Flow sind nur zwei Oberflächen darauf.
2. **Messung nie unterbrechen:** Wert-Änderungen (Ziel, Preise, Hysterese …) werden live übernommen;
   ein Neuladen würde die laufende Viertelstunde ungültig machen.
3. **Importierte Daten überschreiben nie eigene Messungen ohne ausdrücklichen Wunsch** — weder in der
   Monats-History (`overwrite`) noch in der Langzeitstatistik (nur Stunden vor der ersten eigenen).
4. Reine Logik (Parser, Profile, Merge) in `calc.py`, ohne HA-Import, per Unit-Test prüfbar.
5. Keine personenbezogenen Daten in Code, Tests, Doku (Test-CSV synthetisch).

## Entscheidungstreiber

Messkontinuität, Nachvollziehbarkeit für Nutzer:innen (woher kommt ein Wert: gemessen/importiert),
Wartbarkeit durch eine Person.

## Optionen

| Thema | Option A (gewählt) | Option B | Warum A |
|---|---|---|---|
| Einstellungen | Number-Entities schreiben `options`, Update-Listener übernimmt Wert-Schlüssel live | Eigener Zustand in den Number-Entities (RestoreNumber), Options nur Default | B hätte zwei Wahrheitsquellen; Options-Flow und Entity könnten auseinanderlaufen |
| Import-Merge | Import getrennt je Monat speichern (`imported`-Teil), Anzeige kombiniert | Import direkt in die Messwerte addieren | Nur getrennt ist ein erneuter Import idempotent und `overwrite` sauber umsetzbar |
| Statistik-Import | Nur Stunden vor der ersten vorhandenen Statistik-Stunde **und** vor Anlage der Entity | Alle Stunden importieren (Recorder überschreibt) | B würde eigene Messwerte ersetzen |
| Dateizugriff | Pfad relativ zum Config-Verzeichnis, außerhalb nur mit `allowlist_external_dirs`, nur `.csv`/`.txt`, Admin-Service | Beliebiger Pfad | Lastgänge sind personenbezogen; Config-Verzeichnis enthält Secrets |

## Umfang

- `number`: Ziel-Leistung (Slider 2–30 kW), Staffelgrenze, vereinbarte Leistung, Mindestleistung,
  Leistungspreis Stufe 1/2, Hysterese (Kategorie Konfiguration).
- `switch`: Peak-Shaving aktiv (RestoreEntity, Standard aus) — Freigabe für Blueprints.
- `sensor` Lastprofil: 96 Slots heute/gestern/Monatsmaximum/Monatsmittel, DST-fest.
- History 36 Monate mit `billed_kw`, `capacity_cost_eur`, `source`.
- Service `netzentgelt.import_load_profile` (Portal-Export, Langzeitstatistik).
- Blueprints Wallbox/Lastabwurf/Benachrichtigung, Beispiel-Dashboards (Core + apexcharts-card).

## Verifikation

pytest (inkl. Recorder-Fixture für den Statistik-Import und Blueprint-Ausführung im Testharness),
ruff, mypy, hassfest lokal; apexcharts-Konfiguration gegen das Config-Schema der Karte (v2.2.3)
geprüft, Darstellung selbst nur live beim Repo-Owner.

## ADR

| Feld | Inhalt |
|---|---|
| Entscheidung | Options bleiben einzige Wahrheitsquelle; Update-Listener lädt nur bei strukturellen Änderungen neu; Import wird je Monat getrennt von Messwerten gespeichert |
| Treiber | Messkontinuität, Idempotenz des Imports, eine Wahrheitsquelle |
| Alternativen | Zustand in RestoreNumber-Entities; Import in Messwerte einrechnen |
| Warum gewählt | Nur so bleiben Options-Flow und Dashboard synchron und ein zweiter Import verfälscht nichts |
| Konsequenzen | Store wird größer (Profile je Monat, ~100–200 KB bei 36 Monaten); Mittelwertprofil gemischter Monate ist eine Näherung (Überlappung doppelt gewichtet) |
| Follow-ups | apexcharts-Darstellung live prüfen; Blueprints an echter Wallbox testen; § 10 (flexible Entnahme) nach SNE-T-V |
